Conformance

An app installed by zap is a conforming app root. That is the whole point: the layout on disk is the specification, not a convention zap invented.

What an install looks like

~/.apps/org.example.tool/
├── app.toml          # manifest, 0644
├── contents/         # immutable tree, 0755, never written at runtime
├── receipt.toml      # zap's install record, 0644
├── data/             # durable state; kept across upgrades and plain removals
├── cache/            # regenerable; deletable at any time
└── run/              # session-scoped; cleared or ignored at startup
RuleHow zap honours it
Root is ~/.apps/<id> or /opt/apps/<id>, mode 0700 or 0750 --apps-dir and $APP_HOME move the parent; --system selects 0750 and /opt/apps.
app.toml and contents/ are the bundle Copied in as they arrived, after being verified.
Entrypoint resolves to an executable inside contents/ Checked before anything is placed. A bundle that fails the check is not installed.
Exposure is a symlink, or a wrapper setting $APP_ROOT A symlink into contents/ at user scope; a small sh wrapper at system scope, where no default base exists.
data/, cache/, run/ are the app's, created by it, never replaced by an upgrade The swap moves them across from the old tree before discarding it.

The swap

An upgrade never writes into a live tree. The new tree is assembled in a staging directory inside the same scope, the old root is renamed aside, and the new one is renamed in. If the second rename fails the old root is put back, so an interrupted upgrade leaves either the previous install or the new one, never a mixture.

contents/ is therefore always either the old tree or the new one. A native binary already running keeps its old inode until it exits.

receipt.toml

The one file zap adds to the layout, defined by the specification as install state. It is written after the tree is in place, never shipped in a bundle, never read by the app, and deleted with the installation.

[source]
  kind = "release"                # release, repo, or archive
  url = "https://github.com/owner/tool/releases/tag/v1.0.0"
  ref = "v1.0.0"                  # tag, or commit for kind = repo

[artifact]
  name = "org.example.tool-linux-arm64.tar.gz"
  sha256 = "9f2c..."
  fetched_at = "2025-11-24T09:14:02Z"

[installer]
  name = "zap"
  version = "0.1.0"
  at = "2025-11-24T09:14:03Z"

No key is required and unknown keys are ignored, so the shape can grow without breaking a reader. zap list --origin reads the first table; zap update reads it to decide what to fetch again.

Like id, a receipt is a self-asserted record of what the installer did, not a claim about what a bundle contains. It is not proof of authorship, and nothing should treat it as one.

What zap is not

zap behaves as an installer, not as an app. It writes into a scope it did not create, which no confined app may do, so it is judged by the specification's rules for installers: it produces app roots, and it honours the mutability rules for the roots it places.

It does not interpret data/, run app code, register services, restart daemons or migrate data. Data migration is the app's job, keyed off its own schema marker.

Getting the specification

The normative document lives in huyng/app-bundle-spec. Where this page and that document disagree, the document is right.
