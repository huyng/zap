Bundles

A bundle is an app root before it is installed: a manifest and a tree, packed into one archive.

Anatomy

my-tool-1.0.0.tar.gz
└── org.example.tool
    ├── app.toml
    └── contents
        └── bin
            └── tool
  • Exactly one <id>/ directory at the archive root, and its name must equal the manifest's id.
  • Inside it, exactly app.toml and contents/. Nothing else: no install scripts, no receipts, no stray files.
  • contents/ holds the whole app, self-contained. Nothing is fetched when it runs.

app.toml

TOML at the root of the bundle. Unknown keys are ignored. All paths are relative to contents/, never absolute.

FieldRequiredMeaning
idyes Lowercase, dot-separated, at least two segments, characters a-z 0-9 . - _. Stable across versions; it names the app root, so changing it orphans the old one and its data.
nameyes Human-readable name, shown by zap list.
versionyes Opaque string. Display metadata only: no ordering, no compatibility meaning.
entrypointno Executable inside contents/, run in the foreground. Omit it for a bundle that is data or resources only; such a bundle installs but exposes nothing.
descriptionnoShort description.
licensenoSPDX identifier.
homepagenoURL.
iconnoPath inside contents/.
[mime] handlesnoFile types the app opens.

A minimal bundle:

id = "org.example.hello"
name = "hello"
version = "1.0.0"
entrypoint = "bin/hello"

What zap accepts

Three shapes install cleanly, and which one you have is decided by what is inside, not by what you call it.

InputWhat zap does
An archive holding one <id>/ Installed as it is. Its manifest is the truth, including its version.
An archive holding a flat tree, with app.toml at the root The manifest moves up and everything else moves down into contents/. The entrypoint comes from that manifest; identity and version come from where the tree was fetched.
An archive with no manifest at all Installed as a payload: one contents/ and an identifier, nothing exposed. zap never guesses an entrypoint from which files happen to be executable.

A release asset that is already a bundle is adopted, not wrapped again. That is how zap installs tools that publish bundles from their own releases, itself included.

Packing one

zap bundle build/org.example.tool --out dist
zap bundle build/org.example.tool --out dist --os linux --arch arm64

Output is named <id>-<os>-<arch>.tar.gz. The platform tokens matter: zap install <release-url> chooses an asset by matching those words in the file name, so a release built without them is invisible to it.

The archive always holds a single <id>/ directory named from the manifest, so the directory you pass can be called anything. Archives are reproducible: entries are sorted and timestamps fixed, so the same tree always produces the same bytes and a checksum stays meaningful.

A tar.gz is the only format written. It carries executable bits and symlinks, which a bundle needs.

Publishing a release

A project builds its own tree, then packs it. Compiling stays the project's job, because only it knows which files ship.

ID := org.example.tool

bundle:
	GOOS=linux GOARCH=arm64 go build -trimpath -o build/$(ID)/contents/bin/tool .
	cp app.toml build/$(ID)/app.toml
	zap bundle build/$(ID) --out dist --os linux --arch arm64

Attach the archive and a .sha256sum beside it to a GitHub release. zap verifies whatever the release publishes: the digest GitHub computes for the asset, or a checksum file beside it (foo.tar.gz.sha256sum), or one covering the whole release (SHA256SUMS). A mismatch aborts before anything is installed.

What gets installed

~/.apps/org.example.tool
├── app.toml        # from the bundle
├── contents/       # from the bundle, replaced wholesale on upgrade
├── receipt.toml    # written by zap: where it came from
└── data/           # created by the app at runtime, kept across upgrades

cache/ and run/ appear the same way, as the app needs them. All three of data/, cache/ and run/ survive an upgrade untouched.
